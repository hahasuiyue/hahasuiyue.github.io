1. 概述

Netshield SDK 是客户端防护服务 SDK。App 启动 SDK 后，SDK 会启动本地监听服务；业务侧通过规则名调用 getLocalhostPort 获取本地端口，然后访问 http://127.0.0.1:<port> 完成受保护请求。

3. SDK 集成

3.1 Android

第三方 App 接入时引入 SDK AAR，并确保 AAR 中的 native libraries 被打包到 APK/AAB。

import com.netshield.Netshield;

Netshield.startNetshieldService("your_pid", "your_key",
    (result, errorMessage, clientIP) -> {
        if (result == 0) {
            int port = Netshield.getLocalhostPort("tcp;web;80");
            String url = "http://127.0.0.1:" + port;
            // 使用 url 发起业务请求
        } else {
            // 启动失败；展示或记录 errorMessage
        }
    });

3.2 iOS

iOS 接入时将 netshield.framework 加入 App target，并按 Xcode 要求嵌入和签名。对外公开类为 LibNetshield：

#import <Netshield/LibNetshield.h>
[LibNetshield startService:@"your_pid"
                       key:@"your_key"
   completionHandler:^(NSInteger startResult, NSString *errMessage, NSString *clientIP) {
    if (startResult == 0) {
        int port = [LibNetshield getLocalhostPort:@"tcp;web;80"];
        NSString *url = [NSString stringWithFormat:@"http://127.0.0.1:%d", port];
        // 使用 url 发起业务请求
    } else {
        // 启动失败；展示或记录 errMessage
    }
}];
⚠️ 结果极性变更提醒 startResult 早期版本为 BOOL，YES 表示启动成功；当前版本为 NSInteger，0 表示启动成功、非 0 表示失败。升级 SDK 时必须把判断改为 if (startResult == 0)：
  • 只把 block 参数类型从 BOOL 改成 NSInteger、判断条件仍写 if (startResult) 的代码会把成功判成失败、失败判成成功。
  • 若宿主工程仍在使用随旧 framework 分发的头文件（block 参数为 BOOL），编译不会报错，但运行期语义同样被反转，必须连同头文件一起升级。
  • 仅 ObjC 包装层的 block 参数发生了极性变化；C ABI（startNetshieldService）以及 Android / Windows / Linux 的结果约定均为 0 成功、非 0 失败，未变化。

3.3 macOS

macOS 接入时将 netshield.framework 加入 App target，并确认运行时可加载该 framework。

3.4 Windows

Windows 接入时，将 netshield.dll 放在应用可加载目录，例如可执行文件同级目录。应用可以通过导入库链接，也可以在运行时使用 LoadLibrary / GetProcAddress 动态加载 DLL。

#include "netshield.h"
#include <stdio.h>

static void __cdecl onStart(int startResult, const char *errMessage, const char *clientIP) {
    if (startResult == 0) {
        int port = getLocalhostPort("tcp;web;80");
        printf("clientIP=%s, url=http://127.0.0.1:%d\n", clientIP ? clientIP : "", port);
    } else {
        printf("start failed: %s\n", errMessage ? errMessage : getErrMessage());
    }
}

int main() {
    startNetshieldService("your_pid", "your_key", onStart);
    return 0;
}

3.5 Linux

Linux 接入时，确保应用运行时能加载 libnetshield.so。

#include "netshield.h"

static void onStart(int startResult, const char *errMessage, const char *clientIP) {

int main() {

}

3.6 Cocos Creator 2

Cocos Creator 2 接入推荐使用项目级 package。业务代码统一通过 window.Netshield 调用，不需要直接区分平台。

第一步将 Netshield package 放到 Cocos Creator 2 项目的 packages 目录：

<CocosProject>
├── assets
├── packages
│   └── netshield
│       ├── assets
│       │   └── Script
│       │       └── Netshield.js
│       ├── main.js
│       ├── package.json
│       └── native
│           ├── android
│           │   └── netshield-release.aar
│           ├── ios_mac
│           │   ├── ios
│           │   │   └── netshield.framework
│           │   └── mac
│           │       └── netshield.framework
│           └── windows
│               └── netshield.dll
└── project.json

project.json 需要保持项目级 package 目录配置：

{
  "packages": "packages"
}

第二步重启 Cocos Creator。确认 JS 门面已同步到：

<CocosProject>/assets/Script/Netshield.js

第三步按平台准备原生二进制。

Android 需要放置：

packages/netshield/native/android/netshield-release.aar

导出 Android Studio 工程后，请确认 AAR 已进入 app module 依赖，并且 native libraries 被合并到最终 APK/AAB：

find . -name libnetshield.so -print

如果导出的 Android Studio 工程包含多个 module，请构建实际的 application module。

iOS/macOS 需要放置：

packages/netshield/native/ios_mac/ios/netshield.framework
packages/netshield/native/ios_mac/mac/netshield.framework

导出 iOS/macOS 工程后，请确认 netshield.framework 已加入目标 target，并完成嵌入、签名和运行时加载路径配置。

Windows 需要放置：

packages/netshield/native/windows/netshield.dll

导出 Windows 工程后，请确认 netshield.dll 位于可执行文件可加载目录。

第四步在业务脚本中调用：

const result = await window.Netshield.start("your_pid", "your_key");

if (result.startResult === 0) {
    const port = window.Netshield.getLocalhostPort("tcp;web;80");
    const url = "http://127.0.0.1:" + port;
    // 使用 url 发起业务请求。
} else {
    console.log(result.errMessage);
}

3.7 Cocos Creator 3

Cocos Creator 3 接入需要在原生平台 target 创建完成后引入 Netshield CMake 配置。

第一步按以下目录结构放置 Netshield TypeScript 门面、接入文件和平台二进制产物：

├── assets
│   └── netshield
│       └── Netshield.ts
└── native
    └── netshield
        ├── android
        │   ├── NetshieldNativeAndroid.cpp
        │   └── netshield-release.aar
        ├── cmake
        │   ├── CodesignMacBinary.cmake
        │   └── Netshield.cmake
        ├── common
        │   ├── NetshieldNative.h
        │   ├── jsb_netshield_manual.cpp
        │   └── jsb_netshield_manual.h
        ├── ios_mac
        │   ├── NetshieldBridge.h
        │   ├── NetshieldBridge.mm
        │   ├── NetshieldNativeApple.mm
        │   ├── ios
        │   │   └── netshield.framework
        │   └── mac
        │       └── netshield.framework
        └── windows
            ├── NetshieldNativeWindows.cpp
            └── netshield.dll

第二步修改各平台 CMake 配置。

在 native/engine/mac/CMakeLists.txt、native/engine/ios/CMakeLists.txt、native/engine/win64/CMakeLists.txt 中，找到：

add_executable(${EXECUTABLE_NAME} ${CC_ALL_SOURCES})

在其后添加：

set(TARGET_NAME_FOR_NETSHIELD ${EXECUTABLE_NAME})
include(${CC_PROJECT_DIR}/../../netshield/cmake/Netshield.cmake)

在 native/engine/android/CMakeLists.txt 中，找到：

add_library(${CC_LIB_NAME} SHARED ${CC_ALL_SOURCES})

在其后添加：

set(TARGET_NAME_FOR_NETSHIELD ${CC_LIB_NAME})
include(${CC_PROJECT_DIR}/../../netshield/cmake/Netshield.cmake)

Android 还需要在 native/engine/android/app/build.gradle 的 dependencies 中添加 AAR 依赖：

dependencies {
    implementation files('../../../netshield/android/netshield-release.aar')
}

第三步注册 JSB 绑定。

在 native/engine/common/Classes/Game.cpp 中添加头文件：

#include "jsb_netshield_manual.h"

并在 Game::init() 中、BaseGame::init() 之前调用：

install_netshield_manual_bindings();

如果 Cocos Creator 3 运行时报错：

Native netshield bridge is not available on globalThis.netshield.Netshield

说明 TypeScript 层已经执行，但原生 JSB bridge 没有注册到 globalThis.netshield.Netshield。请检查：

  • native/engine/common/Classes/Game.cpp 是否包含 #include "jsb_netshield_manual.h"。
  • Game::init() 中是否在 BaseGame::init() 之前调用了 install_netshield_manual_bindings()。
  • 当前平台的 native/engine/*/CMakeLists.txt 是否在 native target 创建后 include 了 native/netshield/cmake/Netshield.cmake。
  • Android 是否已引入 native/netshield/android/netshield-release.aar。

3.8 Unity

Unity 接入推荐使用 Assets/NetshieldPlugin 作为项目内插件目录，C# 层统一通过 Netshield4Unity 调用。

第一步导入 Unity 插件。发布包如果提供 Netshield.unitypackage，可直接导入；如果提供插件目录，按以下结构放置 Unity 插件文件和平台二进制产物：

<UnityProject>
└── Assets
    └── NetshieldPlugin
        ├── Editor
        │   ├── NetshieldPluginImporterConfigurator.cs
        │   └── NetshieldiOSPostProcessBuild.cs
        ├── Runtime
        │   ├── INetshieldInterface.cs
        │   ├── Netshield.cs
        │   └── impl
        │       ├── Netshield4Android.cs
        │       ├── Netshield4OSX.cs
        │       ├── Netshield4Others.cs
        │       └── Netshield4Windows.cs
        └── Plugins
            ├── Android
            │   └── netshield-release.aar
            ├── iOS
            │   └── netshield.framework
            ├── macOS
            │   └── netshield.framework
            ├── x86
            │   └── netshield.dll
            └── x86_64
                └── netshield.dll

导入 Unity 后，请确认各平台插件的导入设置与目标平台匹配。

第二步按平台准备原生二进制。

Android 需要放置：

Assets/NetshieldPlugin/Plugins/Android/netshield-release.aar

导入 Unity 后请确认插件导入设置中 Android 平台已启用。

iOS 需要放置：

Assets/NetshieldPlugin/Plugins/iOS/netshield.framework

导出 Xcode 工程后请确认 netshield.framework 已加入 target 的 Embed Frameworks，并设置为 Code Sign On Copy。

macOS 需要放置：

Assets/NetshieldPlugin/Plugins/macOS/netshield.framework

Windows 需要按架构放置：

Assets/NetshieldPlugin/Plugins/x86/netshield.dll
Assets/NetshieldPlugin/Plugins/x86_64/netshield.dll

第三步在业务 C# 脚本中调用：

using Netshield;
using UnityEngine;

public class NetshieldExample : MonoBehaviour
{
    private const string Pid = "your_pid";
    private const string Key = "your_key";
    private const string Rule = "tcp;web;80";

    private void Start()
    {
        Netshield4Unity.GetInstance().StartService(Pid, Key, OnNetshieldStarted);
    }

    private void OnNetshieldStarted(int startResult, string errMessage, string clientIP)
    {
        if (startResult != 0)
        {
            Debug.LogError("Netshield start failed: " + errMessage);
            return;
        }

        int port = Netshield4Unity.GetInstance().GetLocalhostPort(Rule);
        if (port <= 0)
        {
            Debug.LogError("Netshield local port unavailable, rule=" + Rule);
            return;
        }

        string url = "http://127.0.0.1:" + port;
        Debug.Log("Netshield clientIP=" + clientIP + ", url=" + url);
        // 使用 url 发起业务请求，或交给业务 WebView/HTTP 客户端访问。
    }

    private void OnApplicationQuit()
    {
        Netshield4Unity.GetInstance().StopService();
    }
}
注意事项
  • GetLocalhostPort 应在 StartService 成功回调后调用。
  • StartService 回调会投递回调用 StartService 时的同步上下文；建议在 Unity 主线程调用 StartService。
  • Android 若出现 SDK Java 类加载失败，优先检查 AAR 是否已导入 Unity 工程，并确认 Android 插件导入设置已启用。

3.9 Flutter

Flutter 接入推荐使用 netshield4flutter plugin。业务侧统一通过 Dart API 调用。

第一步将 netshield4flutter plugin 放到 Flutter 项目可访问的位置，并在业务 App 的 pubspec.yaml 中添加依赖：

dependencies:
  netshield4flutter:
    path: ../path/to/netshield4flutter

第二步拉取 Flutter 依赖：

cd <FlutterApp>
fvm flutter pub get

第三步确认 Android Maven 仓库配置。

如果发布包使用本地 Maven 仓库，宿主 Flutter App 的 Android 工程需要能解析该仓库。例如：

allprojects {
    repositories {
        maven {
            url uri("${rootProject.projectDir}/../../android/local-maven")
        }
        google()
        mavenCentral()
    }
}

实际路径以业务 App 与 netshield4flutter plugin 的相对位置为准。

第四步在 Flutter 业务代码中调用：

import 'package:netshield4flutter/netshield4flutter.dart';

final sdk = Netshield4flutter();

Future<void> startNetshield() async {
  final result = await sdk.startService('your_pid', 'your_key');

  if (!result.isSuccess) {
    print('Netshield start failed: ${result.errMessage}');
    return;
  }

  final port = await sdk.getLocalhostPort('tcp;web;80');
  if (port <= 0) {
    print('Netshield local port unavailable');
    return;
  }

  final url = 'http://127.0.0.1:$port';
  print('Netshield clientIP=${result.clientIP}, url=$url');
  // 使用 url 发起业务请求，或交给业务 WebView/HTTP 客户端访问。
}

Future<void> stopNetshield() async {
  await sdk.stopService();
}

第五步按目标平台构建。

cd <FlutterApp>
fvm flutter build apk --release
fvm flutter build ios --release
fvm flutter build macos --release
fvm flutter build windows --release

iOS 模拟器不能使用 fvm flutter build ios --release。如需模拟器测试，应使用：

fvm flutter build ios --simulator
fvm flutter run -d <simulator-id>
注意事项
  • getLocalhostPort 应在 startService 成功返回后调用。
  • macOS release 如需网络访问或本地监听，请确认 App entitlements 中包含相应网络权限。
  • Windows 构建或运行 Flutter Windows App 前，系统可能需要开启开发者模式，以允许 Flutter 插件使用 symlink。
  • Windows 构建产物需要能在可执行文件目录加载到 netshield.dll。

第四步制作并运行自定义基座。

  • getLocalhostPort 应在 startNetshieldService 成功回调后调用。
  • iOS 模拟器必须使用包含模拟器架构的 netshield.framework。

3.11 UniApp Native Plugin

UniApp Native Plugin 接入适用于传统原生插件机制的 UniApp 项目。业务侧通过 uni.requireNativePlugin 获取插件对象，Android 和 iOS 的原生实现由 native plugin 包提供。

第一步按 UniApp Native Plugin 规范准备插件目录：

<UniAppProject>
├── manifest.json
├── pages.json
└── nativeplugins
    └── netshieldNativePlugin
        ├── package.json
        ├── android
        │   ├── NetshieldUniAppNativeBridge-release.aar
        │   └── netshield-debug.aar
        └── ios
            ├── NetshieldUniAppNativeBridge.framework
            └── netshield.framework

第二步按平台准备原生二进制。

Android 需要确认 native plugin 声明了插件类：

com.netshield.NetshieldUniAppNativeBridge

并声明或合并以下权限：

<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
<uses-permission android:name="com.google.android.providers.gsf.permission.READ_GSERVICES" />

iOS 需要确认 native plugin 包含：

NetshieldUniAppNativeBridge.framework

如果 iOS 需要在 HBuilderX 中运行调试，应先制作自定义基座，确保 NetshieldUniAppNativeBridge.framework 被嵌入并签名。

第四步在业务代码中调用：

const netshieldNativePlugin = uni.requireNativePlugin('netshieldNativePlugin');

netshieldNativePlugin.startNetshieldService("your_pid", "your_key", (ret) => {
    if (ret.startResult == "0") {
        const port = netshieldNativePlugin.getLocalhostPort("tcp;web;80");
        const url = "http://127.0.0.1:" + port;
    } else {
        console.log(ret.errMessage);
    }
});

netshieldNativePlugin.stopNetshieldService();
注意事项
  • Native Plugin 接入后，App 调试应使用自定义基座；标准基座不会内置该原生插件。
  • iOS framework 如包含动态库，需要加入 Embed Frameworks 并在打包时签名。
  • Android 如出现类找不到或 native library 加载失败，请检查 native plugin 包结构、AAR 是否进入最终 APK，以及 manifest merge 结果。

4. 初始化与业务流程

SDK 没有单独的初始化对象或配置对象。启动接口即初始化入口。建议在应用启动后、业务请求发起前尽早启动 SDK。

标准流程：

准备 pid/key
  ↓
调用 start/startService/startNetshieldService
  ↓
等待启动回调
  ↓
startResult == 0：读取 clientIP，按 rule 查询本地端口
startResult != 0：展示/记录 errMessage

启动成功后，业务侧使用 getLocalhostPort(rule) 获取本地监听端口，并访问 http://127.0.0.1:<port> 发起受保护请求。getLocalhostPort 返回 -1 表示未找到规则、SDK 未启动成功或内部状态不可用。

参数说明：

参数类型必填说明示例
pidstring / const char * / NSString *是客服提供的 pid123
keystring / const char * / NSString *是客服提供的 key示例中为 32 位字符串
callback / completionHandler函数/闭包Android/Windows/Linux 可为空；iOS 示例应传入启动完成回调见示例

7. 网络与安全

SDK 可确认的网络/安全行为：

  • SDK 启动时会启动本地服务。
  • 业务侧请求应访问 http://127.0.0.1:<port>。
安全提示 不要在业务日志中打印真实 key。文档和 Demo 中的 pid/key 仅用于示例，不应作为生产配置。

8. 生命周期管理

阶段API说明
启动/初始化start...异步启动；通过回调判断结果。
使用getLocalhostPort(rule)启动成功后调用，得到本地监听端口。
停止stop...可在应用退出或不再需要防护服务时调用，释放 SDK 资源。

重复启动：

  • SDK 会通过服务状态防止重复启动。
  • Android 正在启动时会回调 -1 和 netshield service is starting。
  • 已启动后再次启动可能返回 -1 和 netshield service has been started.。
  • 防护 SDK 通常按进程生命周期启动一次，不建议业务侧设计运行期重启流程。
  • 调用停止接口后，已获取的本地端口不应继续使用；如需再次访问，应重新启动 SDK 并重新查询端口。

10. FAQ

现象：启动回调中 startResult != 0。

原因：

  • pid 或 key 为空。
  • pid/key 与服务端配置不匹配。
  • 当前网络无法拉取配置。
  • SDK 初始化失败。
  • 本地目录或设备标识获取失败。

排查方式：

  • 确认传入的 pid、key 来自客服提供。
  • 打印并上报启动回调中的 errMessage。
  • 检查设备网络是否可访问外网。
  • Android 检查 App 是否有 INTERNET 和 ACCESS_NETWORK_STATE 权限。
  • 桌面平台检查二进制依赖是否完整。

解决方案：

  • 修正 pid/key。
  • 网络恢复后重新调用启动接口。
  • 如果 errMessage 指向目录权限或设备标识，检查运行目录、沙盒权限和系统权限。

现象：返回 netshield service is starting 或 netshield service has been started.

原因：

  • 上一次启动尚未回调。
  • SDK 已经处于启动成功状态。

排查方式：

  • 检查业务代码是否重复点击启动按钮或并发调用启动 API。
  • Android 示例中使用 startingSDK 防止重复点击。

解决方案：

  • 启动期间禁用启动按钮。
  • 已启动后不要再次调用启动；防护 SDK 通常随进程运行，不建议业务侧设计主动重启流程。

现象：启动后查询规则端口返回 -1。

原因：

  • SDK 尚未启动成功。
  • 传入的 rule 不存在或与服务端配置不匹配。
  • SDK 启动流程失败或尚未进入可用状态。

排查方式：

  • 确认只在启动成功回调后调用。
  • 检查规则名是否与服务端配置一致。
  • 记录启动回调中的 errMessage。

解决方案：

  • 等待启动成功后再查端口。
  • 使用服务端实际下发的规则名。
  • 启动失败时不要继续发起本地请求。

现象：端口已获取，但访问本地地址失败。

原因：

  • getLocalhostPort 返回 -1，业务仍拼接 URL。
  • 本地服务未启动或不可用。
  • 规则对应的上游网络不可达。
  • Windows/桌面平台可能存在权限或安全软件拦截。

排查方式：

  • 检查端口值是否大于 0。
  • 确认请求发生在启动成功之后。
  • 记录 HTTP 状态码和网络错误。

解决方案：

  • 端口为 -1 时不要发起请求。
  • 网络恢复后重试。
  • Windows 场景检查应用权限和防火墙/安全软件策略。

现象：启动失败信息包含 timeout，例如 startup timed out while waiting for network。

原因：

  • 网络状态长期不可用。

排查方式：

  • 检查设备网络。
  • Android/iOS/macOS 检查 WebView/WebKit 是否可正常加载页面。

解决方案：

  • 提示用户切换网络或稍后重试。
  • 允许用户重新启动 SDK。

现象：启动失败或配置拉取失败，错误信息指向网络安全链路。

原因：

  • 当前公开 API 没有证书配置项；证书和安全链路由 SDK 内部处理。
  • 设备网络、代理、证书环境异常可能导致内部请求失败。

排查方式：

  • 记录 errMessage。
  • 检查系统时间、代理、抓包工具和企业网络证书策略。

解决方案：

  • 关闭异常代理/抓包环境后重试。
  • 将完整 errMessage 提交给技术支持。

现象：调用启动接口后业务层没有收到回调。

原因：

  • 应用进程过早退出。
  • 桌面 C ABI 示例没有保持主线程/事件循环。
  • 包装层回调对象被业务层释放。

排查方式：

  • 确认进程在异步启动完成前仍然存活。
  • Unity/Cocos/Flutter 使用 SDK 发布包提供的官方包装层，不要直接绕过包装层调用 native API。
  • Windows/Linux C ABI 接入时确认 callback 函数生命周期足够长。

解决方案：

  • 在启动完成前保持页面/对象存活。
  • 对 C/C++ 应用，用 condition variable、事件循环或消息循环等待回调。

现象：回调里更新 UI 崩溃或无效。

原因：

  • Windows/Linux 基础 C ABI 未确认会回调到 UI 主线程。
  • 业务层直接调用基础 C ABI 后在回调中更新 UI。

排查方式：

  • 确认当前使用的是基础 SDK 还是 Flutter/Unity/Cocos/UniApp 包装层。
  • 基础 C ABI 使用方自行切回 UI 线程。

解决方案：

  • Android Java SDK 回调已投递到 Android 主线程。
  • iOS/macOS LibNetshield 回调已投递到主线程。
  • Flutter/Unity/Cocos/UniApp 使用 SDK 发布包提供的官方包装层。
  • Windows/Linux 原生 App 在回调里手动投递到 UI 线程。

现象：启动或请求过程中崩溃。

原因：

  • native 二进制和包装层版本不匹配。
  • 缺少 DLL/SO/dylib/framework 或 ABI 不匹配。
  • 重复启动、并发初始化或生命周期调用异常。
  • 平台依赖缺失。

排查方式：

  • 确认使用同一批 SDK 产物。
  • Android 检查 ABI 和 .so 是否打包。
  • Windows 检查 netshield.dll 是否在加载路径中。
  • iOS/macOS 检查 framework 是否嵌入和签名。
  • 记录崩溃堆栈和 errMessage。

解决方案：

  • 重新集成匹配的二进制。
  • 避免重复启动或并发初始化。
  • 将崩溃堆栈、平台、系统版本、SDK 产物版本提交给技术支持。

现象：开发者希望按错误码分类处理。

原因：

  • 当前公开接入按启动成功或失败处理，并同时返回错误字符串。

排查方式：

  • 查阅本文 "API Reference" 中的返回值约定。

解决方案：

  • 业务侧按 startResult == 0 判断成功。
  • 失败时展示或上报 errMessage。

现象：开发者希望配置 Server URL、代理、证书、超时。

原因：

  • 当前公开 API 没有网络配置项。

排查方式：

  • 公开接入 API 主要用于启动、端口查询和错误信息查询。

解决方案：

  • 将需求（目标 Server、代理方式、超时要求等）提交给客服，由技术支持配置并下发。
